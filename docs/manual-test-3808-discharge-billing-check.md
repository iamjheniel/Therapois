## Deployed shape

| | |
|---|---|
| Row | **id 55, `billing_discharge_management_timing`** |
| Timing / severity / group | `billing` / `error` / `time` (Zeit) |
| Insurance | `['public']` — GKV only, Privat Basis off per #3708 AC3 |

**A NEW description shipped** rather than a second row under the creation key — which is the safer
of the two options the Developer Reference laid out, because older migrations update by
description alone and would otherwise hit both rows.

**The billing row covers Blanko and the creation row (id 14) does not.** Deliberate: the rule
applies to every VO marked Entlassmanagement, as the RC 3.14 expiry rule does.

## The Developer Reference's open question, answered

It asked someone to *"check how the Validation Configuration screen lists two rows with the same
label"*. Both keys resolve to **"Entlassmanagement-Timing"**, and the screen does show two rows —
but under **different section headings**, `Erstellungsprüfungen` and `Abrechnungsprüfungen`, so
they are distinguishable. No change needed.

## Where the note lives

AC4's text is generated by the API, so it is **not in the frontend bundle** — searching there for
"Behandlungen außerhalb des Zeitraums" returns 0, which reads like it was never implemented. It is
served as **`autoNote`** on `GET /prescription_validations?prescription=<id>`, and is **omitted
when the check passes** rather than being empty.

Verified verbatim against the Localization Reference, e.g. for 100019-1:

```
Entlassmanagement: Behandlungen außerhalb des Zeitraums
(Ausstellung: 01.09.2026, Beginn bis: 08.09.2026, Ende: 13.09.2026): 14.09.2026.
```

## Traps

- **The verdict filter is the bare `prescription=`.** `prescription.id=` is accepted and silently
  ignored: 18 rows against 200, so every VO appears to carry a hundred verdicts belonging to
  others.
- **No stored verdict ≠ the check not applying.** 100020-1, 100033-1, 100034-1 and 100036-1 have
  **zero** verdicts for *any* check — they are Aktiv, issued 4 Oct, never validated. An oracle that
  reads "absent" as "the check did not run for this insurance type" reports four false mismatches
  (mine did, first time round).
- `autoNote` is **omitted** when the check passes, so a key-list taken from a passing row does not
  show it at all.

## What the automated file writes, and why that is safe

One test drives AC5 on **100019-1** and is self-restoring by construction:

1. `PATCH /prescription_validations/{id}` `{passed:true}` — the manual **Pass**.
2. `POST /prescriptions/{id}/check-billing-validation` — **Erneut prüfen**, which puts the
   automatic `false` and its note straight back. That *is* AC5 row 2, so the undo is the test.
3. `PATCH /prescriptions/{id}` `{isDischargeManagement:false}` + re-check — the check passes
   (AC5 row 3) — then the marker is restored and re-checked in a `finally`.

Observed: the verdict row is **updated in place** (same id 592896 throughout), not recreated.

Nothing else needs doing by hand. The PM's own walkthrough (9489-1 → Re-check → Pass) is the same
three steps on a different VO.
